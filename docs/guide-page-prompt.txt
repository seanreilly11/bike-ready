# Guide Page — Spec & Implementation Prompt

## Overview

The Guide section is a free, publicly accessible reference area containing 6 module study guides, a 74-term Dutch cycling glossary, and a combined signs teaching page with visual reference. All content is server-rendered for SEO and lives on dedicated routes that Google can index individually.

The Signs & Signals module guide has been merged into the Signs reference page — the teaching content is interleaved with the visual sign reference so you read the concept and immediately see the signs. This means there are 6 study guides (not 7), and the Signs tab handles all sign-related content in one place.

The UI feels like a single tabbed page with drill-down navigation, but each view is a real Next.js route with its own URL, page title, and meta tags.

---

## Route structure

```
/guide                         → Landing: module list (Guides tab active)
/guide/[moduleId]              → Individual module guide (6 pages)
/guide/glossary                → Full glossary with search + filters
/guide/signs                   → Signs page: teaching content + visual reference combined
```

All routes share a common layout with the BikeReady nav bar and the bottom tab bar. The Guide section tabs (Guides / Glossary / Signs) appear at the top of the shared layout and use `next/link` for navigation — not client-side state.

### Full URL list

```
/guide                         → Guide landing (6 module cards)
/guide/fundamentals            → Fundamentals guide
/guide/priority                → Priority Rules guide
/guide/roadusers               → Road Users guide
/guide/infrastructure          → Infrastructure guide
/guide/legal                   → Legal Rules guide
/guide/vocabulary              → Vocabulary guide
/guide/glossary                → Glossary
/guide/signs                   → Signs: teaching + visual reference
```

9 routes total. No `/guide/signs-signals` — the signs module guide content has been folded into `/guide/signs`.

### Dynamic metadata for module guides

```ts
// /guide/[moduleId]/page.tsx
import guides from '@/data/guides.json'

export async function generateMetadata({ params }: { params: { moduleId: string } }) {
  const guide = guides.find(g => g.moduleId === params.moduleId)
  if (!guide) return {}

  return {
    title: `${guide.title} — Dutch Cycling Guide | BikeReady`,
    description: guide.subtitle,
    openGraph: {
      title: `${guide.title} — Dutch Cycling Guide`,
      description: guide.subtitle,
      url: `https://bikeready.nl/guide/${guide.moduleId}`,
    },
  }
}

export async function generateStaticParams() {
  const guides = (await import('@/data/guides.json')).default
  return guides.map(g => ({ moduleId: g.moduleId }))
}
```

## Shared layout

```
app/guide/layout.tsx
```

The shared layout wraps all guide routes. It renders:

1. The BikeReady top nav bar (logo + page context)
2. The three section tabs: Guides | Glossary | Signs
3. The bottom tab bar (Practice / Review / Guide / Test)

The section tabs use `next/link` with the `usePathname` hook to determine the active tab:

```tsx
// app/guide/layout.tsx
import Link from 'next/link'
import { usePathname } from 'next/navigation'

const SECTION_TABS = [
  { href: '/guide', label: 'Guides', match: (path: string) => path === '/guide' || (path.startsWith('/guide/') && !path.startsWith('/guide/glossary') && !path.startsWith('/guide/signs')) },
  { href: '/guide/glossary', label: 'Glossary', match: (path: string) => path.startsWith('/guide/glossary') },
  { href: '/guide/signs', label: 'Signs', match: (path: string) => path.startsWith('/guide/signs') },
]
```

**Important:** The section tabs should NOT appear when the user is inside a module detail page (`/guide/[moduleId]`). In that state, show the back button + module name + sticky ToC instead. Detect this by checking if the route matches a known moduleId.

```tsx

const isModuleDetail = guides.some(g => pathname === `/guide/${g.moduleId}`)

{isModuleDetail ? (
  // Show: ← back button + module emoji + title + horizontal ToC
) : (
  // Show: Guides | Glossary | Signs tabs
)}
```

## Page components

### /guide/page.tsx — Guide landing (module list)

Server component. Reads `guides.json`. Renders 6 module cards in a vertical list.

Each card is a `Link` to `/guide/[moduleId]`:

```tsx
<Link href={`/guide/${guide.moduleId}`}>
  <div className="module-card">
    <span className="emoji">{guide.emoji}</span>
    <div>
      <h3>{guide.title}</h3>
      <p>{guide.subtitle}</p>
    </div>
    <span className="topic-count">{guide.sections.length} topics</span>
    <span className="chevron">›</span>
  </div>
</Link>
```

No client-side state needed. Pure server render.

### /guide/[moduleId]/page.tsx — Module detail

Server component. Reads the matching guide from `guides.json`. Renders the subtitle, then each section as a heading + paragraphs.

**Sticky horizontal ToC** at the top (inside the layout, see above). Each ToC pill is an anchor link to the section heading:

```tsx
<a href={`#section-${i}`} className="toc-pill">
  {section.heading}
</a>
```

Each section heading has a matching id:

```tsx
<h3 id={`section-${i}`}>{section.heading}</h3>
```

**Previous/Next navigation** at the bottom of each guide:

```tsx
const idx = guides.findIndex(g => g.moduleId === moduleId)
const prev = idx > 0 ? guides[idx - 1] : null
const next = idx < guides.length - 1 ? guides[idx + 1] : null
```

Renders two Link cards: "← Previous: Fundamentals" and "Next: Road Users →".

### /guide/glossary/page.tsx — Glossary

This is a **client component** (`'use client'`) because it needs search and filter interactivity.

Reads `glossary.json`. Renders:
1. Header (eyebrow, heading, subtitle, term count)
2. Search input — filters by Dutch term or English translation
3. Category chips — horizontally scrollable, filters by category
4. Results count — dynamic: "12 terms in Prohibitions matching 'ver'"
5. Term cards — each with an `id` attribute for anchor linking

```tsx
<div id={term.term.replace(/\s+/g, '-').toLowerCase()}>
  {/* term card content */}
</div>
```

This means `/guide/glossary#haaientanden` scrolls directly to that term. Useful for sharing specific terms and for Google's passage indexing.

**Empty state** when no terms match the search/filter combination.

### /guide/signs/page.tsx — Signs: teaching + visual reference (merged)

This page combines the signs teaching content (formerly a separate module guide) with the visual sign reference. The teaching flows into the reference — you read the concept and immediately see the relevant signs.

It is a **client component** (`'use client'`) for the expandable sections and smooth scroll ToC.

Reads `signs-reference.json`. The page renders in this order:

1. **Header** — "Dutch cycling signs" title, subtitle explaining the visual grammar concept
2. **Sticky horizontal ToC** — scrollable pills for each section (How to read any sign, Blue circles, The end-of pattern, Red borders, Sub-signs, Priority signs, Your traffic light, Information signs)
3. **Design system overview** — 2×2 grid of rule cards explaining shape/colour grammar (circles = commands, triangles = warnings, rectangles = info, diamond = priority). Each card has a coloured left border matching its category. Below the grid: an orange callout with the quick rule summary.
4. **Blue circles — mandatory** — prose paragraph explaining the concept, immediately followed by sign cards showing the actual SVGs (mandatory cycle path G11, footpath G7, cyclists & mopeds route G12a). Each sign card shows the SVG, name, Dutch name, RVV code, and description.
5. **The end-of pattern** — prose explanation of the red sash and grey lines convention. Rendered as side-by-side comparison cards: active sign → arrow → end-of variant. Shows mandatory cycle path active vs end-of, and priority road active vs end-of. The visual comparison is the key — this concept is hard to explain in words but immediately clear when shown.
6. **Red borders — prohibition** — prose paragraph, then sign cards for no cycling (C14), no entry (C2), road closed (C1), no pedestrians (C16).
7. **Sub-signs** — prose explaining the modifier concept. Rendered as a combined visual: the no-entry sign stacked above the uitgezonderd sub-sign, exactly as they appear on a real post. Explanation text beside it.
8. **Priority signs & markings** — prose about priority road diamond and shark teeth. Sign cards for both.
9. **Your traffic light** — prose about the cyclist traffic light. Sign card showing the cyclist light SVG.
10. **Information signs** — prose about rectangular information signs. Cards for optional cycle path (fietspad) and fietsstraat. Ends with a highlighted comparison callout: mandatory (round blue, "Must use") vs optional (white rectangle, "Your choice") shown side by side.

Each sign renders its SVG using the `component` key from the JSON:

```tsx
import { SIGN_COMPONENTS } from '@/components/signs/SignRegistry'

const SignComponent = SIGN_COMPONENTS[sign.component]
if (SignComponent) return <SignComponent />
```

This reuses the exact same SVG components already built for the question cards.

## Navigation behaviour

| Action | What happens |
|---|---|
| Tap Guides tab | Navigate to `/guide` — module list (6 modules) |
| Tap a module card | Navigate to `/guide/[moduleId]` — section tabs hidden, back button + ToC shown |
| Tap ← back in module detail | Navigate to `/guide` |
| Tap Previous/Next at bottom of guide | Navigate to `/guide/[otherModuleId]` — scroll resets to top |
| Tap Glossary tab | Navigate to `/guide/glossary` |
| Tap Signs tab | Navigate to `/guide/signs` — full signs page with teaching + reference |
| Tap a ToC pill in module detail | Smooth scroll to that section's anchor on the same page |
| Tap a ToC pill on signs page | Smooth scroll to that section's anchor on the same page |
| Search in glossary | Client-side filter — no route change |
| Tap category chip in glossary | Client-side filter — no route change |

## Accessibility

- All section headings use semantic `<h2>` and `<h3>` tags — not styled divs
- The search input has a `<label>` (can be visually hidden) and `aria-label="Search Dutch or English terms"`
- Sign SVGs have `role="img"` and `aria-label` with the sign name
- The ToC pills use `<a href="#section-N">` for native anchor behaviour (or buttons with scrollIntoView)
- Category filter chips use `aria-pressed` to indicate the active filter
- Module cards in the list are `<a>` tags (via `Link`), not buttons — they navigate
